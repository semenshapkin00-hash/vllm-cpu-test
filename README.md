# CPU инференс vLLM в Minikube

Репозиторий решения: https://github.com/semenshapkin00-hash/vllm-cpu-test

Решение тестового задания Data Engineer для команды исследования технологий машинного обучения. Модель — `Qwen/Qwen2.5-0.5B-Instruct`, vLLM — `0.27.0+cpu`. Инференс выполняется на CPU без квантизации с `dtype=float16`. Сборка рассчитана на **Linux ARM64**, в том числе Minikube внутри Docker Desktop на Apple Silicon.

## Локальный запуск

Нужны Docker с Linux ARM64, Minikube `1.37.0`, kubectl `1.34.x`, Python `3.12` для вспомогательных скриптов. Стенд — Apple M2 с 16 ГБ RAM; Docker выделено около 8 ГБ. Кластеру выделяется 6 CPU и 6000 МБ, контейнеру модели — 4 CPU, до 5 GiB RAM; PVC — 3 GiB. GPU не требуется и в манифестах не запрашивается.

Для чистой сборки и импорта образов рекомендуется запас 20 GiB свободного места на диске хоста: промежуточные слои сборки и временные копии образов занимают дополнительное место.

Распакуйте ZIP-архив или клонируйте репозиторий командой `git clone https://github.com/semenshapkin00-hash/vllm-cpu-test.git`. После получения исходников выполните:

```bash
cd vllm-cpu-test

# Для выбранной открытой модели HF_TOKEN можно не задавать.
# При необходимости gated-модели экспортируйте свой HF_TOKEN заранее.
python3 scripts/create_secrets.py
bash scripts/build.sh
bash scripts/deploy.sh

# Оставьте процесс работающим в отдельном терминале.
kubectl --context vllm-cpu -n vllm-cpu port-forward service/vllm 8000:8000
```

`create_secrets.py` сохраняет случайный API-токен и значение `HF_TOKEN` в `.secrets/` с правами `0600`; существующие файлы не перезаписывает. `deploy.sh` создаёт Kubernetes Secret `vllm-secrets` из этих файлов. Значения не входят в образ, ConfigMap, аргументы запуска или Git. Bearer-токен получает только основной контейнер, HF-токен — только initContainer. Для изменения токенов обновите файлы и повторите создание Secret и перезапуск Deployment. В локальном Minikube Secret не предполагает отдельной настройки шифрования etcd; доступ к нему контролируется доступом к кластеру.

Проверка запроса без вывода API-токена:

```bash
python3 - <<'PY'
import json
from pathlib import Path
from urllib.request import Request, urlopen
payload = {"model": "qwen-cpu", "messages": [
    {"role": "user", "content": "Кратко объясни назначение индекса в базе данных."}
], "max_tokens": 64, "temperature": 0}
request = Request("http://127.0.0.1:8000/v1/chat/completions",
    json.dumps(payload).encode(), {
        "Content-Type": "application/json",
        "Authorization": "Bearer " + Path(".secrets/api-token").read_text().strip()
    })
with urlopen(request, timeout=300) as response:
    print(json.load(response)["choices"][0]["message"]["content"])
PY
```

Сервис имеет тип `ClusterIP`; port-forward слушает localhost. Middleware требует Bearer-токен для HTTP-запросов, кроме служебных `/health`, `/metrics` и `/ping`, включая `/v1/*` и `/tokenize`. `/health` используется Kubernetes-пробами без токена. Стандартная проверка API-ключа vLLM также включена.

## Образы и зависимости

Собственный `Dockerfile` устанавливает официальный **CPU wheel** vLLM `0.27.0` и CPU-сборку PyTorch. `requirements.txt` фиксирует всё дерево Python-зависимостей, включая транзитивные; для vLLM используется неизменяемый URL релиза и SHA256, для остальных пакетов — точные версии и SHA256. Установка выполняется с `--no-deps --require-hashes --only-binary=:all:`, затем `pip check`. Образ Python закреплён по digest. Запуск дополнительно проверяет CPU-бэкенд, версию vLLM и отсутствие CUDA в PyTorch.

Отдельный `downloader/Dockerfile` собирает лёгкий образ загрузчика с `huggingface-hub`, без vLLM и PyTorch. Его полное дерево зависимостей зафиксировано в `downloader/requirements.txt`. Оба образа запускаются с `USER 10001:10001`. В Pod заданы `runAsNonRoot`, `allowPrivilegeEscalation: false`, `capabilities.drop: [ALL]`, `readOnlyRootFilesystem` и `seccompProfile: RuntimeDefault`; токен ServiceAccount не монтируется.

Файлы `.in` нужны только для осознанного обновления lock-файлов. Сборка использует готовые `.txt` и не разрешает версии заново. Команда обновления — `bash scripts/lock.sh` с `uv 0.12.10`. После обновления зависимостей выполните сборку образов и тесты.

## Кэш модели на PVC

`download-model` — отдельный initContainer. Он скачивает веса и токенизатор с HF строго по ревизии `7ae557604adf67be50417f59c2c2f167def9a775` в каталог PVC `/models/<revision>`. Сначала загрузка идёт во временный каталог, затем создаётся `.ready.json` с размерами и SHA256 файлов; проверенный каталог переименовывается атомарно. Незавершённая загрузка не считается готовой. Файловая блокировка исключает одновременную запись.

При последующем запуске скрипт проверяет локальные файлы **до импорта клиента HF** и завершает работу с событием `model_cache_hit`. При неповреждённом кэше сетевых обращений нет. При неполном или повреждённом кэше выполняется повторная загрузка. Основной контейнер читает PVC только для чтения и всегда работает с `HF_HUB_OFFLINE=1`, `TRANSFORMERS_OFFLINE=1` и локальным путём модели.

## ConfigMap и Kustomize

Все манифесты находятся в `k8s/`, включая `kustomization.yaml`:

```bash
kubectl --context vllm-cpu apply -k k8s
```

Secret создаётся отдельно командой из `scripts/deploy.sh`; реальные значения намеренно не хранятся в YAML. Для первоначального деплоя используйте весь `deploy.sh`: он также загружает образы в Minikube. В манифестах установлен `imagePullPolicy: Never` для локальных образов.

Параметры инференса находятся в `k8s/configmap.yaml`: `server.json` содержит `max_model_len`, `max_num_seqs`, `max_num_batched_tokens`, `dtype`, настройки chunked prefill и prefix caching. Там же заданы размер CPU KV-кэша и параметры OpenMP (`nobind` и 4 потока для лимита в 4 CPU). `enableServiceLinks: false` исключает конфликт автоматически создаваемой Kubernetes переменной `VLLM_PORT` с одноимённой настройкой vLLM. После изменения ConfigMap:

```bash
kubectl --context vllm-cpu apply -k k8s
kubectl --context vllm-cpu -n vllm-cpu rollout restart deployment/vllm
kubectl --context vllm-cpu -n vllm-cpu rollout status deployment/vllm --timeout=10m
```

Пересборка образов не нужна. При смене модели согласованно измените `MODEL_ID`, `MODEL_REVISION` и локальный путь `model` в `server.json`; для gated-модели запишите подходящий токен в Secret. `trust_remote_code` не включён. `Recreate` предотвращает конкуренцию старого и нового Pod за локальные ресурсы и RWO-том.

## Приватное логирование

`app/logging.json` применяется и к vLLM через `VLLM_LOGGING_CONFIG_PATH`, и к Uvicorn через `--log-config-file`. `app/privacy.py` заменяет форматирование стандартных логов: сообщения, аргументы и traceback не выводятся, поскольку они могут содержать промпты, ответы или секреты. Для них остаются только время, уровень и событие `runtime_log`. Это сознательно ограничивает детализацию диагностики.

Логирование запросов и ответов vLLM отключено флагами `--no-enable-log-requests` и `--no-enable-log-outputs`; стандартный access log Uvicorn также отключён. Собственный ASGI middleware пишет `request_end` с серверным случайным ID, фиксированным именем маршрута, HTTP-методом, статусом и длительностью. Тела, заголовки, query string, клиентский ID и произвольный URL не логируются. Для streaming событие появляется после окончания обработки потока, включая ошибочные запросы. Частые `/health` и `/metrics` в аудит не включаются.

## Проверки

```bash
python3 -m unittest discover -s tests -v
# При работающем port-forward:
python3 scripts/verify_endpoint.py
# Пересоздаёт Pod с HF offline и недоступным HF endpoint, затем восстанавливает env:
python3 scripts/verify_offline_restart.py
```

Unit-тесты проверяют отсутствие пользовательских данных в логах, аудит streaming и ошибок, пропуск клиента HF при попадании в кэш, обнаружение повреждения и прерванной загрузки. Интеграционные тесты проверяют UID, CPU, ответы `401` без токена и с неверным токеном, `200` с правильным токеном, отклонение некорректного запроса, потоковую генерацию, защиту `/tokenize` и отсутствие промпта, ответа, API-токена и произвольного URL в stdout/stderr контейнера. Для отправленных запросов проверяется наличие записей аудита. Результаты — в `results/verification.json` и `results/offline-restart.json`.

## Нагрузочное тестирование

```bash
python3 scripts/benchmark.py --input-tokens 32 1024 --concurrency 1 4 \
  --requests 8 --output-tokens 32 --warmups 2 --output results/benchmark.json
```

Тест использует streaming `/v1/completions` и фиксированные входы ровно по 32 и 1024 токена. Токены получаются через `/tokenize` из повторяющегося текста об индексах БД, затем обрезаются до нужной длины. У каждого запроса ровно 32 выходных токена (`ignore_eos=true`, `temperature=0`, `seed=42`). По два прогревочных запроса на сценарий исключены из замеров. Prefix caching отключён, чтобы повторяющиеся входы не ускоряли prefill за счёт кэша. Сырые ответы и промпты в отчёты не записываются.

TTFT измеряется от начала HTTP-запроса до первого непустого текстового фрагмента SSE, Latency — до `[DONE]`. Они включают очередь, HTTP и port-forward. Throughput считается за общее время сценария с ограниченной параллельностью: завершённые запросы/с и сгенерированные выходные токены/с. Значения p95 рассчитываются линейной интерполяцией; восемь запросов дают только небольшой локальный замер, а не устойчивую оценку хвостовой задержки. При ошибке или несовпадении числа токенов тест завершается с ошибкой.

Замеры проведены 26 октября 2026 года на Apple M2, 16 GiB RAM, Linux ARM64 в Minikube 1.37.0 и Kubernetes 1.34.0. Для API установлен лимит 4 CPU и 5 GiB RAM, FP16, KV-кэш 1 GiB, `max_model_len=2048`, `max_num_seqs=4`, `max_num_batched_tokens=1024`, OpenMP 4 потока. Все 32 измеряемых запроса завершились успешно.

| Вход токенов | Параллельность | Запросов | TTFT mean мс | TTFT p95 мс | Latency mean мс | Latency p95 мс | Запросов/с | Выходных токенов/с |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 32 | 1 | 8 | 164.95 | 170.16 | 1250.64 | 1402.35 | 0.799 | 25.58 |
| 32 | 4 | 8 | 430.43 | 518.83 | 1875.76 | 1890.06 | 2.127 | 68.06 |
| 1024 | 1 | 8 | 2657.36 | 2730.50 | 3701.98 | 3812.33 | 0.270 | 8.64 |
| 1024 | 4 | 8 | 6848.16 | 10862.88 | 12584.57 | 17059.81 | 0.317 | 10.14 |

Для короткого входа переход от одного к четырём одновременным запросам увеличил Throughput с 25,58 до 68,06 выходных токенов/с. Для длинного входа рост составил с 8,64 до 10,14 токена/с, при этом средний TTFT вырос с 2,66 до 6,85 с. В этом замере длинный prefill и очередь ограничивают выигрыш от параллельности; одно увеличение числа одновременных запросов не даёт пропорционального роста скорости.

Параметры и сведения о стенде — `results/environment.json`; отдельные замеры, p50 и p95 — `results/benchmark.json`. Таблица также формируется автоматически в `results/benchmark.md`.

## Как повысить Throughput

**А — много коротких запросов.** В первую очередь увеличивать `max_num_seqs` с 4, например до 8, затем до 16, и повторять тест с соответствующей клиентской параллельностью. Continuous batching позволяет обрабатывать больше последовательностей за один шаг decode. `max_num_batched_tokens` должен позволять заполнить этот batch, но его увеличение сверх реальной нагрузки само по себе не ускоряет модель. Размер KV-кэша должен вмещать одновременно активные запросы; при вытеснениях увеличить `VLLM_CPU_KVCACHE_SPACE` в пределах RAM. Для короткого ввода и приоритета задержки decode уместен chunked prefill с умеренным бюджетом токенов. Prefix caching имеет смысл включить только при действительно повторяющихся префиксах. Число потоков OpenMP и их привязку следует согласовать с выделенными CPU, избегая переподписки.

**Б — меньше запросов с большим контекстом.** Увеличить `max_model_len` до необходимого размера контекста с учётом выхода и возможностей модели. Увеличивать `max_num_batched_tokens` с 1024 до 2048, затем до 4096, чтобы prefill обрабатывал более крупные порции ввода, и сравнивать Throughput и TTFT, проверяя пиковую память. Chunked prefill оставить включённым: он ограничивает размер порции длинного запроса и позволяет планировщику чередовать prefill с decode. Слишком малый бюджет дробит длинный ввод на много шагов; слишком большой ухудшает задержку других запросов и увеличивает рабочую память. Выделить больше RAM под KV-кэш, а `max_num_seqs` ограничить числом длинных контекстов, которые реально помещаются, чтобы избежать вытеснений и повторных вычислений. Prefix caching ускорит повторную обработку общих длинных префиксов, но не поможет для уникальных контекстов.

Обе группы изменений — направления для последующих замеров, а не заявленные результаты оптимизации. На CPU скорость также ограничивают пропускная способность памяти и число доступных ядер; параметры с `gpu` в имени не означают использование GPU. В данном решении размер CPU KV-кэша задаётся явно через `VLLM_CPU_KVCACHE_SPACE`.

Документация: [планировщик и chunked prefill vLLM 0.27.0](https://docs.vllm.ai/en/v0.27.0/configuration/optimization/), [CPU backend vLLM 0.27.0](https://docs.vllm.ai/en/v0.27.0/getting_started/installation/cpu/), [настройки логирования](https://docs.vllm.ai/en/v0.27.0/examples/features/logging_configuration/), [модель Qwen](https://huggingface.co/Qwen/Qwen2.5-0.5B-Instruct).
